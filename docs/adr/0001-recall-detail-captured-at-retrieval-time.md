# 召回明细在检索当时落库（turn_recall）

RAG 审计需要回答"每轮检索命中了哪些知识条目、得分多少、谁被重排丢弃"。ES 侧候选块的
chunk_id 是 ingest 时生成的随机 uuid，不含 knowledge_id，检索结束后无法由 chunk_id 反查归属
知识条目；候选材料也只存在于检索当轮的内存 state 中。因此决定在检索节点内联捕获融合后
top20 候选（知识 id/标题/名次/得分），经 `_persist`（门户与开放接口共用落库点）写入
`turn_recall` 表，重排节点补记"是否保留"。

## 后果

- **存量历史轮次没有召回明细**——功能上线前的轮次无法补齐（当时未捕获即永久丢失）。
- 行数约束：仅检索型轮次、每轮 top20，行量可控；不按子查询拆分（多子查询命中取最优名次）。
- 若未来把 chunk_id 改为确定性编码（如 `knowledge_id:seq`），事后关联才成为可能，本设计可再评估。

## 备选方案（已否）

- 阶段表 output_data 里已存 rerank kept 的 chunk_id 列表——同样因 chunk_id 不可回溯而无法审计，且无得分明细。
- 新建"材料快照表"按 snapshot_id 存全文——存储代价高，且展示来源快照（display_snapshot）已覆盖人工查看场景。
